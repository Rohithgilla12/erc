# ERC website Phase 1 design

Status: scaffolded, 2026-10-19. Domain types live in [`packages/domain`](../packages/domain/src/index.ts). The original whole-system sketch, [`20261019-erc-phase-1-types.ts`](20261019-erc-phase-1-types.ts), is kept only for the CMS and data-access signatures not yet in code.

Evidence labels: **[V]** verified on 2026-10-19 with the URL given, **[I]** inferred, **[G]** guess.

## Decision

Use **Payload CMS 3.x inside the Next.js app, on Postgres**. One deploy, one database, one admin at `/admin`. Editorial content and structured records are separated by structure inside that one system, not by running two systems.

Hosting (revised 2026-10-19): ERC has no revenue, so every component is free and open source where one exists. Everything runs on `boxy`, an existing free-tier Arm server in **Hyderabad** shared with other personal projects, as a Docker Compose project published through a Cloudflare Tunnel, with media and downloads on Cloudflare R2's free tier. Running cost is US$0; the only spend is a domain.

## Framework: Next.js, not TanStack Start or Astro

Versions checked on npm on 2026-10-19 **[V]**: `payload` and `@payloadcms/next` 3.91.0; `@payloadcms/tanstack-start` exists only as `4.0.0-beta.2`; `@tanstack/react-start` 1.169.3; `astro` 7.4.0; `next` 16.4.2.

The framework is chosen by the CMS, not the other way round. Payload's admin panel is a Next.js app in every stable release.

```
 Next.js (chosen)               TanStack Start                 Astro
 ┌────────────────────┐         ┌────────────────────┐         ┌──────────┐  ┌────────────────┐
 │ site + /admin +    │         │ site + /admin +    │         │ site     │  │ Next.js app    │
 │ Payload, one app   │         │ Payload 4 BETA     │         │ (Astro)  │  │ for /admin only│
 └─────────┬──────────┘         └─────────┬──────────┘         └────┬─────┘  └───────┬────────┘
           v                              v                         └──── Postgres ───┘
        Postgres                       Postgres                    two apps, two builds, two containers
 stable today                   adapter is beta only            stable, but the admin still needs Next
```

- **TanStack Start** is a good framework (stable 1.x, Vite, type-safe routing). Payload's adapter for it ships only in the 4.0 beta, and Payload's own announcement calls the demo early **[I]** (secondary summary of https://payloadcms.com/posts/blog/payload-40-admin-ui-redesign-tanstack-mcp-and-more). Launching a club site on a beta CMS adapter is the wrong risk.
- **Astro** is the best tool for a pure content site: zero JavaScript by default. But the admin still needs Payload's Next.js app, so ERC would run two apps. Phases 2 and 3 are app-shaped (accounts, dashboards, leaderboards, checkout), where Astro's islands model adds friction. Payload's Local API does run outside Next.js **[V]** https://payloadcms.com/docs/local-api/outside-nextjs, but no Astro integration is documented.
- **Next.js** runs the site, admin, and API in one process with the in-process Local API. It is the only option that is one app and stable today.

**Keeping the door open.** Payload 4's adapter design keeps the same Payload config across frameworks **[I]**. Everything that is not a page lives outside the framework: domain logic in `packages/domain`, and the Payload config in plain TypeScript. Switching the site to TanStack Start after Payload 4 is GA would then replace one app folder, not the system.

## Repository layout

A pnpm workspace with Turborepo (MIT). Verified on 2026-10-19: `turbo run typecheck` and `turbo run build` pass, the `linux/arm64` image builds, and it serves `/` with data from `@erc/domain`.

```
erc/
├── apps/
│   ├── web/                 @erc/web: Next.js 16 + Payload 3.91 (site, /admin, REST, GraphQL)
│   │   ├── src/app/(frontend)   public pages
│   │   ├── src/app/(payload)    admin and API routes, generated by Payload
│   │   ├── src/collections      Payload collections (to become defineEditorial / defineRecord)
│   │   └── Dockerfile           turbo prune, then a standalone build
│   └── mobile/              later: Expo app, added when there is a real need
├── packages/
│   ├── domain/              @erc/domain: framework-free TypeScript (types, units, parsers, rules)
│   └── tsconfig/            @erc/tsconfig: shared strict base
├── infra/boxy/              compose.yaml and .env.example for the server
├── docs/
├── turbo.json, pnpm-workspace.yaml, package.json
```

What makes a future mobile app cheap, and how each part is enforced rather than hoped for:

1. **Domain code runs anywhere.** `@erc/domain` compiles with `lib: ["ES2022"]` and `types: []`, so a reference to `document`, `window`, `FormData`, or Node's `fs` fails the build. React Native's Metro bundler can import it unchanged **[I]**. Verified: a test file using `document` fails `tsc`.
2. **One public entry point.** The package's `exports` map exposes only `src/index.ts`. Verified: a deep import such as `@erc/domain/src/primitives` fails to compile, and so does importing the internal `notImplemented`.
3. **Parsers take plain data.** `parseRaceQuery` takes a params record and `parseRaceSubmission` takes a field record, not `URLSearchParams` or `FormData`. The web form and a mobile form share validation.
4. **The API boundary arrives with the client.** Phase 1 web reads in-process through the Local API. When the mobile app starts, `apps/web` gains versioned route handlers (`/api/v1/races`) that return `@erc/domain` types, and a `packages/api-client` is added. Payload's auto-generated REST stays internal, because its documents are CMS wire shapes. Phase 2 member auth must issue bearer tokens, not cookie-only sessions, so the same login works on a phone.
5. **No shared UI package yet.** Web uses React DOM and mobile would use React Native. Sharing components across them costs more than it saves at this size. Design tokens can become a package when the mobile app exists.

Turborepo's `prune` builds the web image from only `@erc/web` and its dependencies, so adding `apps/mobile` never changes or rebuilds the server image.

## Problem

Phase 1 ships Home, About, Coaching and Contact pages; a blog and video CMS; a searchable race calendar; free training plans and downloads; a basic athlete directory with manually maintained achievements; SEO, analytics, newsletter signup, and a mobile-first layout. News and paid plans are not Phase 1.

The shape is non-obvious because the brief asks for two things that pull against each other. Its decision table says to keep editorial content separate from athlete, event, result, and payment data. Phases 2 and 3 need those two sides to reference each other constantly: a race report cites a race and an athlete, and a paid plan is both an article and a product. Two systems make the separation easy and every cross-reference hard. One system makes references easy and needs the separation enforced some other way.

Assumptions, not asked: editors are two to five non-technical coaches; the budget is small; one part-time developer fluent in TypeScript, Next.js, and Postgres; readers mostly in India on mid-range Android over 4G; videos are YouTube embeds; no content migration at launch.

## Usage (the caller's view)

A coach logs in at `/admin` and sees two sidebar groups. **Content** holds posts, videos, plans, resources, pages, coaches, and topics, with Draft, Submit for review, Publish, Schedule, and Preview. **Records** holds races, athletes, results, subscribers, and enquiries, with Approve and Reject and no rich-text body.

A developer reads only through `src/content/*` and `src/domain/*`. Importing `payload` from a site route fails lint.

```ts
// app/(site)/races/page.tsx
export default async function RacesPage({ searchParams }: Props) {
  const today = todayIn('Asia/Kolkata')
  const query = parseRaceQuery(await searchParams, today)
  const page = await findRaces(query)                  // approved, upcoming, filtered, faceted, cache-tagged
  return <RaceCalendar page={page} query={query} />    // chips are links built by serialiseRaceQuery
}

// src/cms/collections/races.ts
export const Races = defineRecord<RaceDoc>({ slug: 'races', route: (r) => `/races/${r.slug}`, intake: 'public-submissions', fields })

// src/cms/collections/posts.ts
export const Posts = defineEditorial<PostDoc>({ slug: 'posts', route: (p) => `/learn/${p.slug}`, fields })
```

## Shape, built up in steps

### Step 1. One app, one database

```
  phone browser
       |
       v
 +-----------------------------+
 | Next.js app (one deploy)    |
 |  app/(site)   public pages  |
 |  app/(payload) /admin + API |
 +--------------+--------------+
                |  Payload Local API, in-process, no HTTP hop
                v
           +----------+
           | Postgres |
           +----------+
```

The site calls Payload in the same process. There is no CMS network hop and no API token to rotate **[I]**.

### Step 2. Separate editorial from records inside it

```
 +---------------------------- Postgres ----------------------------+
 |  EDITORIAL  (defineEditorial)       RECORDS  (defineRecord)       |
 |  posts videos trainingPlans         races athletes results        |
 |  resources pages coaches topics     subscribers enquiries media   |
 |  - drafts, versions, review flow    - moderation: submitted,      |
 |  - rich text                          approved, rejected          |
 |  - public when published            - typed units, no rich text   |
 |                                     - public when approved        |
 |              \______ may reference ______^                        |
 |              records never reference editorial                    |
 +------------------------------------------------------------------+
```

The separation lives in structure, not in a convention someone must remember:

1. **Two constructors, one list.** `defineEditorial` and `defineRecord` are the only way to build a collection, and `buildErcConfig` accepts only their output. `EDITORIAL_SLUGS` and `RECORD_SLUGS` are the single classification; admin grouping, access rules, and cache invalidation derive from membership.
2. **Different lifecycles.** Editorial content has one stored `workflow` field, `live` plus `revision`, driven by the pure `transition()` state machine; Payload's `_status` on the main row is written from `live`, never edited separately. Records share one `Moderation` union, changed only by `decide()` in a hook, used by race submissions now and by profile claims and results in Phase 2.
3. **One-way references.** Editorial may point at records. Records never point at editorial, so deleting a post can never orphan a result.
4. **Typed units.** Metres, seconds, paise, and `LocalDate` (`YYYY-MM-DD`) are branded. A race date is a local fact; a timestamp would shift it across midnight for anything computing in UTC.
5. **Derive, never store twice.** Distance `category` (PB slot) and `band` (calendar filter) are written only by a hook from `metres`. Personal bests come from `deriveAchievements(results)`. Plan length is `weeks.length`. Verification staleness is computed from `lastVerifiedOn`.

The ownership rule for every future entity: **people curate or moderate it, so it is a Payload collection; members or machines write it at volume, so it is a plain app table read through SQL views.**

### Step 3. Rendering and caching

```
 phone ── Cloudflare edge ── cached? ──yes──> served, boxy not touched
                               │ no
                               v
                       cloudflared tunnel (outbound only, no open port)
                               v
                 boxy, Hyderabad: erc-web (Next.js + Payload) ── erc-postgres
                               ^
 coach publishes ── Payload afterChange hook ── revalidateTag(collectionTag(slug), { expire: 0 })
```

- Reads are cached in Next.js's data cache and tagged per collection (`collection:races`). `defineEditorial` and `defineRecord` append the `afterChange` and `afterDelete` hooks that expire the tag, so a new collection cannot forget to invalidate. `revalidateTag` is idempotent, so a retried hook is harmless. The hook calls `revalidateTag` first; Next can only expire tags inside a request it is serving, so when it reports that there is no request (a `payload run` script, or in-process work outside a request such as the job queue) the hook sends the tags to `POST /api/revalidate` on `ERC_SITE_URL`, authorised by `REVALIDATE_SECRET`. Production refuses to start without either variable (`apps/web/src/site-config.ts`), because a missing site URL would point every canonical link at localhost.
- Race pages render per request from those cached reads, so they work without JavaScript, return real 404s, and read today's IST date per request. Next.js 16 Cache Components were tried and rejected for now: with them every route streams a static shell first, so a missing race returns a soft 200 unless a proxy checks the database, and anything behind `<Suspense>` needs JavaScript to appear. Prerendering landing pages at build time also needs a database inside the image build, which the Dockerfile does not have.
- Cloudflare caches only immutable assets (`/_next/static`, uploaded images) at the edge. HTML is cached by Next.js on boxy, so a publish is live immediately with no edge purge to wire up **[I]**.
- `erc-web` is a long-running Node server, not serverless, so Payload's job queue runs in-process with `autoRun` **[V]** https://payloadcms.com/docs/jobs-queue/overview. The race list cache is keyed on today's IST date, so lists roll over at midnight with no job. The queue handles scheduled publishing and email. No external cron.
- Images upload to a public R2 bucket through Payload's S3 storage adapter (MIT; R2 speaks the S3 API) with Payload-generated sizes, served from an R2 custom domain on Cloudflare's edge. Pages use those sizes directly, so there is no image service and boxy serves no image bytes. YouTube uses a click-to-load facade, so a video page ships no YouTube script until tapped.
- Performance budget: LCP under 2.5 s and under 100 KB of JavaScript on content pages, on a mid-range Android over 4G **[G]**. Server Components by default; the calendar filter is a plain GET form that works without JavaScript.
- SEO: per-document SEO fields; JSON-LD for `Article`, `VideoObject`, `Event`, and `Person`; sitemap and RSS built from published documents; drafts and unapproved records are unreachable because anonymous read access is a Payload where-clause, not page logic. The race calendar's list reads use raw SQL, which bypasses access control, so they also carry their own `moderation_state = 'approved'` predicate, and `parseRaceDoc` rejects anything else; keep all three guards.
- Analytics: Umami, self-hosted, MIT-licensed, cookieless, storing its data in its own database inside `erc-postgres` **[I]**. Google Search Console (free) for search data.

### Step 4. The race calendar

Dominant read: approved races starting on or after today, filtered by discipline, distance band, state, and "registration open", optional text, sorted by date, 24 per page.

| Filter | Storage | Index |
|---|---|---|
| date window | `dates_start` as `YYYY-MM-DD` text | btree |
| discipline | select | btree |
| distance band | `races_distances.band` | btree on `(band, parent_id)` |
| state | `location_subdivision` (`IN-TS`, `IN-AP`) | btree |
| text | `name`, `location_city` | `pg_trgm` GIN |
| visibility | `moderation_state = 'approved'` | partial index |

- `findRaces` returns the page plus **facet counts**: each chip's count is the result total of the query its link leads to (`tapChip`). Discipline and band are multi-select, so an unselected chip counts the current selection plus that value and a selected chip counts the view after removing it; a state chip replaces or clears the one state. Each family's counts come from one statement of `count(*) FILTER (WHERE ...)` columns, one per chip. `serialiseRaceQuery` is the inverse of `parseRaceQuery`, so chips are plain links and any filtered view is shareable on WhatsApp.
- Bands are exhaustive (under 10K through over 100K) so trail races at 25K or 35K are filterable. Categories (5K, 10K, half, marathon, standard ultras) remain the PB slots.
- Indexable landing pages exist only for single facets: `/races/discipline/trail`, `/races/in/telangana`, `/races/in/andhra-pradesh`. `canonicalPathOf` and `nearestLandingPath` in `@erc/domain` decide this. Multi-facet and text views are `noindex` with a canonical to the nearest landing page, which avoids crawl traps; filter chips to them carry `rel="nofollow"`.
- Each race shows its typed `source` (organiser, listing site, runner submission, or coach knowledge, shown as "ERC coaches" and stored as the confirming staff account, never a coach profile), `lastVerifiedOn`, official link, registration deadline, and `status`. Postponed and cancelled races stay listed with a badge. Races not verified in 90 days show "not recently checked" and appear on a stale list in the admin.
- "Save to my calendar" is a per-race `.ics` with a stable UID, plus a Google Calendar link. No account needed.
- Public race submissions land as `submitted` records behind ALTCHA (MIT, proof-of-work, no third party), a honeypot field, and a per-IP rate limit, idempotent on normalised name plus start date.
- Caching is bounded by what a chip or a page link can reach. Free-text searches and custom date windows are read uncached, an unknown slug is answered from the cached list of approved slugs, and a page past the end redirects (307) to the last page, so anonymous input cannot grow `.next/cache/fetch-cache`.
- Scale: perhaps 1,000 to 3,000 races a year **[G]**. Postgres with trigram search is enough; no search service.

### Editor workflow

A document keeps what readers see (`live`) apart from the working copy (`revision`), so an edit to a published post goes through the same review as a new post.

```
 live       none ────────────── publish ──────────────> published ── unpublish ──> none
                                   ^                                  (revision kept)
 revision   draft ──submit──> in_review ───────────────┘ publish clears the revision
              ^                 ├ request_changes ──> changes_requested ──submit──> in_review
              │                 └ schedule(at) ──> scheduled ──(no job yet)
            edit (opens a draft on a published document; drops a schedule)
```

Authors can edit and submit. Editors and admins also request changes, publish, schedule, and unpublish. In the admin, Save Draft is an edit, Publish is `publish`, and Unpublish is `unpublish`; authors see Save Draft only. Submit for review and Request changes are a Review choice in the sidebar that the next save applies. A draft save writes only a version stamped `draft`, so an anonymous `?draft=true` read never sees an unpublished revision. Live preview shows the draft on the real page through Next.js draft mode. Version history gives restore.

### Hosting and cost

The host is `boxy`, a free-tier Arm server in Hyderabad with Docker and Compose, shared with other personal projects that are published the same way. Operational details of the host live in the operator's private notes, not in this public repository.

```
 boxy (free-tier Arm, Hyderabad)              compose project: erc
 ┌───────────────────────────────────────────────────────────────────┐
 │ erc-cloudflared ──> erc-web :3000 (Next.js + Payload, arm64) ──────┼──> R2 public bucket (images)
 │                         │                                          │    R2 private bucket (downloads)
 │                         v                                          │
 │                    erc-postgres (postgres:17-alpine)               │
 │                         └── /data/media/erc/pg                     │
 │                    erc-umami (analytics) ── same Postgres, own DB  │
 └───────────────────────────────────────────────────────────────────┘
        nightly host backup ── pg_dumpall ──> encrypted off-host restic repository
```

Boxy holds only state that is small and already backed up (Postgres). Bulky, cacheable bytes live in R2, so neither boxy's disk nor its bandwidth grows with the media library.

| Item | Cost | Licence | Evidence |
|---|---|---|---|
| boxy compute and storage | US$0 | n/a | free tier, already provisioned **[V]** |
| Payload, Next.js, Postgres, Umami, ALTCHA, Nodemailer, listmonk | US$0 | MIT, MIT, PostgreSQL, MIT, MIT, MIT, AGPL | **[I]** |
| Cloudflare Tunnel and DNS | US$0 | client Apache-2.0; service is free, not open source | **[I]** |
| Cloudflare R2 (media, downloads) | US$0 under 10 GB, no egress fees | free, not open source | **[V]** https://developers.cloudflare.com/r2/pricing/ (checked by the cross-judge) |
| Gmail SMTP relay | US$0 | not open source | **[G]** limits |
| Backups | US$0 | restic (BSD) | the host's nightly backup already dumps every Postgres container **[V]** |
| Domain | about US$10 a year | n/a | **[G]** |

The three components that are free but not open source are the Cloudflare Tunnel, R2, and the SMTP relay. R2 was accepted on 2026-10-19 because it keeps media off boxy's disk and out of its backup, and serves images from the edge. Exiting R2 is a storage-adapter config change, since it speaks the S3 API. The tunnel is kept because it matches how boxy already publishes apps, needs no inbound port, and puts Cloudflare's edge cache in front of a single box. The fully open alternative is nginx with Let's Encrypt, which needs inbound HTTPS opened on the host's firewall.

Hyderabad is the best possible origin for a Telangana and Andhra Pradesh audience. Even an uncached page is one short hop away.

Capacity: ERC adds well under 1 GB of RAM across its containers (about 200 MB measured at idle), with memory limits set in compose. Two constraints matter:
- **The root disk is tight.** Postgres data, the page cache, and local uploads therefore live on a separate large volume under `/data/media/erc`, and uploads move to R2. The `erc-web` image is the only thing that lands on the root disk.
- **R2 is durable storage, not a backup.** A deleted object is gone. Payload keeps the upload records in Postgres, which is backed up nightly. Whether to also sync the buckets into the restic run is an open question.

Build and deploy: `infra/boxy/ship.sh` builds the committed HEAD as a `linux/arm64` image on a workstation (the shared host never builds), streams it over SSH with `docker load`, and runs `deploy.sh`, which dumps the database, swaps the image tag, waits for health, and keeps three images for rollback. Every ERC container opts out of automatic image updates, because an upgrade can carry a Payload migration. Payload's `prodMigrations` runs pending migrations on boot.

Risks of one box: no redundancy, and a host outage takes the site down except for assets cached at the edge. That is accepted for a club site with no revenue. The exit is unchanged. The same image runs anywhere Docker runs, and Postgres moves with `pg_dump`.

### Step 5. Phase 2 grows the same database and admin

```
 +--------------------------------- Postgres ----------------------------------+
 | EDITORIAL           RECORDS (Payload)              APP TABLES (ours)          |
 | + challenges        + members (auth)               activities                 |
 |                     athletes.member -> members     saved_races                |
 |                     results (+ self_reported)      v_mileage_weekly, ...      |
 |                     claims (moderation)            (SQL views)                |
 +-----------------------------------------------------------------------------+
```

- **Accounts.** A `members` auth collection separate from `staff`, so `/admin` stays staff-only. A member claims an existing athlete profile through the same moderation flow. No athlete data moves.
- **Results and approval.** `results` already carries provenance and moderation. The admin list filtered to `submitted` is the approval queue.
- **Mileage and leaderboards.** Activities go into an app table because the volume and write pattern are not editorial. Leaderboards are SQL views that drop hidden athletes before ranking, with weekly, monthly, age-group, and experience views. Heart rate is never a leaderboard; HR and pace progress stay private per member.
- **Challenges.** Definitions are editorial. Progress derives from activities. A badge is written once per (challenge, athlete) when a challenge closes, idempotently.

### Step 6. Phase 3 adds money without touching editorial


## Synthesis decision

Three structurally different designs were produced in parallel and judged against a six-point rubric (editor autonomy, Phase 2 and 3 runway, cost and operations, content model, interface depth, vendor risk).

| Candidate | Shape | Judge | Mine |
|---|---|---|---|
| 1 | Payload inside Next.js, Postgres | 26 | 25 |
| 2 | Sanity hosted CMS plus a separate Postgres | 20 | 22.5 |
| 3 | Keystatic, content as git files, static site | 22 | 22 |

**Base: candidate 1.** Both judges picked it independently. A maintainer adds a collection through one of two constructors and inherits access, admin grouping, and invalidation. Every Phase 2 and 3 cross-reference is a foreign key in one database, so the brief's invariants (verified versus self-reported, hidden athletes excluded, one access gate) live in one place. Candidates 2 and 3 both end up with cross-store IDs that have no foreign key, plus a mirror table or a nightly check, and two admin tools by Phase 2.

**Grafted:**
- From candidates 2 and 3: race `status` (scheduled, postponed, cancelled). The base could not represent a cancelled race.
- From candidate 3: typed `source` and a derived 90-day staleness flag on `lastVerifiedOn`.
- From candidate 2: facet counts on the calendar and a query serialiser that inverts the parser.
- From candidate 3: an explicit mobile performance budget.
- From candidate 2: the one-sentence ownership rule, merged with the base's volume rule.

**Fixed during synthesis:**
- The base stored editorial state twice, in Payload's `_status` and a custom `stage`. Now `workflow` is the only owner and `_status` is written from it.
- The base's distance categories left trail distances such as 25K unfilterable. Exhaustive bands were added for filtering.
- Race submissions no longer accept derived fields from a form.

**Rejected:**
- Sanity's two admin tools in Phase 1 and its public-by-default dataset, which would leak paid content in Phase 3 without a paid plan.
- Keystatic's GitHub-based publishing: 3 to 5 minutes to go live, a custom publish gate, and a pre-1.0 editor.
- Running on Cloudflare Workers via OpenNext. It saves about US$15 a month but adds risk to a Postgres-backed Payload for one part-time developer.

## Implementation reconciliation

Deviations accepted while moving the sketch into `packages/domain` on 2026-10-19, at the operator's request for a mobile-ready structure:

- `serialiseRaceQuery` returns a query string, not `URLSearchParams`, and `parseRaceSubmission` takes a field record, not `FormData`. This keeps the package free of DOM types. The contract is unchanged.
- `Id` is generic over an entity name rather than a CMS collection slug, so the domain does not depend on the CMS.
- Image references in domain types are URLs (`photoUrl`), not CMS media ids. Resolving media is the content layer's job.
- `payloadStatusOf` and everything that touches Payload (`defineEditorial`, `defineRecord`, `collectionTag`, `findRaces`) stay in `apps/web`.
- `canAccess` is implemented as "always allow", which is exactly the Phase 1 policy.

## Trade-offs accepted

- We accept that every schema change is a code change and a deploy, in exchange for a typed schema reviewed in pull requests and no drift between environments. Coaches cannot add fields themselves.
- We accept coupling CMS uptime to site uptime, in exchange for no network hop, one bill, and one auth model. Cached pages keep serving if a render fails.
- We accept Payload's generic admin, which is plainer than Sanity Studio for writers **[G]**, in exchange for owning the data and sharing it with Phases 2 and 3. A one-page editor guide covers the gap.
- We accept running the site on one shared personal server with no redundancy, in exchange for US$0 running cost. Edge-cached assets survive an outage; pages do not.
- We accept being our own database administrator (upgrades, disk, restores), in exchange for no managed-database bill. The existing nightly restic backup carries most of it.
- We accept three free but proprietary services (Cloudflare Tunnel, R2, and an SMTP relay), because the open alternatives cost an open port, disk on a full server, or deliverability. All three are swappable through configuration, not code.
- We accept a Figma-owned upstream with Payload Cloud paused **[V]** https://payloadcms.com/payload-has-joined-figma, in exchange for an MIT codebase **[V]** we could fork. Custom admin components stay minimal to keep upgrades cheap.

## Alternatives considered

- **Sanity plus a separate Postgres.** It has the best writing studio and costs about US$6 a month. It lost because coaches use two admin tools from day one, the review gate on the free plan can be bypassed, cross-store IDs have no foreign key, and free datasets are publicly queryable **[V]** https://www.sanity.io/pricing.
- **Keystatic with git-backed static files.** It is the cheapest option with the least lock-in. It lost on editor autonomy: publishing takes 3 to 5 minutes, there is no review queue, the editor is pre-1.0, and Phase 2 adds a whole second app.
- **Directus or Strapi beside the Next.js app.** Same database story, but a second always-on service, and the schema lives outside the codebase. Directus is now under the Monospace Sustainable Core License, free for organisations under US$5M revenue and 50 employees **[V]** per the cross-judge, https://directus.com/docs/licensing/overview.
- **Payload on Cloudflare Workers.** The official template uses D1 (SQLite), which weakens Phase 2 analytics. Postgres there needs Hyperdrive **[V]** https://blog.cloudflare.com/payload-cms-workers/. It is kept as a later option because Payload is portable.
- **Vercel Pro plus Neon (the first version of this design).** About US$21 a month, managed, and redundant. It was dropped on 2026-10-19 because ERC has no revenue and an always-free Hyderabad server already exists. Moving back is an image deploy and a `DATABASE_URL` change.

## Open questions

- Build on Payload 3.91 now and upgrade at 4.0 GA, or start on the 4.0 beta? Recommendation: 3.x **[V]** https://github.com/payloadcms/payload/releases.
- Do tables added through `beforeSchemaInit` appear in `payload migrate:create`? This needs a prototype before Phase 2 relies on one migration system.
- Will content need Telugu or Hindi? Payload localisation changes field storage, so it is cheaper to decide before launch.
- Who moderates race submissions and results, and how quickly? The calendar's credibility rests on `lastVerifiedOn` being honest.
- Phase 2 login: email magic link or phone OTP? Payload auth is password-first **[I]**, so OTP means a custom strategy.
- Does ERC have an existing site? The brief's "keep this" on the performance dashboard suggests one. Its stack and data decide whether Phase 1 needs an import.
- Which domain? A new one costs about US$10 a year; a subdomain of a domain already on Cloudflare costs nothing.
- Should the ERC repository be public? Open source fits the "all free" goal and gives free Arm runners on GitHub Actions **[I]**.

## Next implementation step

The race calendar is built: `src/content/races.ts`, the `/races` pages, and `src/scripts/seed-races.ts`. ## Known gaps (2026-10-19)

Closed by workstream C: the editorial workflow (review H1, H2, M1), race moderation (review M2) with submitter details stored, staff deletion that dropped races, and race slugs shadowed by landing routes.

Remaining correctness gaps:

- The domain can schedule a revision, but no job publishes it at `publishAt`, so the admin does not offer Schedule yet.
- An anonymous `?draft=true` read by id of a published document with a pending revision returns 404 rather than the live copy, because Payload reads only the latest version. Public pages do not make draft reads.
- Staff deletion is refused by a hook. The foreign keys from races to staff still set null, so a delete made in SQL bypasses the guard.

Product and later work:

- `.ics` for a postponed race uses the original start date.
- Writes made inside the server but outside a request, such as the job queue's scheduled publishing, still revalidate over HTTP through `ERC_SITE_URL`, because Next has no request store for `revalidateTag` there. A tunnel failure leaves those pages stale for up to an hour, with a warning in the log.
- Uncached views (text search, custom dates) cost six SQL statements each, twice that past page 1, and have no rate limit yet; a Cloudflare rate-limit rule on `/races*` is the planned defence.
- No sitemap yet, and no admin list of stale races.
- A state-led filter will want a partial index on `(location_subdivision, dates_start)` for approved races as the table grows (inferred from the EXPLAIN plans at 3,000 rows).
- Image sizes and remote image patterns for the R2 domain.
